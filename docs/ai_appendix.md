# AI Workflow Appendix

Documenting where AI helped, what it actually contributed, one moment it was confidently wrong, and how I caught it. Using AI is a skill; showing my judgment about *when to trust it* is the point of this section.

## How I used AI

I used an LLM (Claude) as a pair — for scaffolding, for arguing a modelling choice, and for catching my own sloppiness — not as an autopilot. Every decision below was mine to accept or reject; the appendix records both.

| Stage | What I asked | What the LLM contributed | What I kept / changed |
|---|---|---|---|
| Cleaning | "How should I handle a rent value of ₹60,00,000 in a monthly-rent feed?" | Argued it's a sale price that leaked in, not an extreme rent — so **drop the record, don't winsorise**. | Kept. Wrote it up as a documented decision in `data_quality_note.md`. |
| Feature choice | "Should I predict rent or log(rent)?" | Rent is right-skewed and multiplicative (a premium locality *scales* rent), so model `log1p(rent)` and back-transform errors to rupees via `expm1`. | Kept — the cross-validated overfitting gap stayed small (0.009), which supported it. |
| Model spec | "Why does my model price a lone 8BHK at ₹1.27 crore?" | A **raw** area term under a `log(rent)` target predicts `exp(b·area)`, which explodes for a huge flat — a specification bug. Enter **`log(area)`** instead for a constant-elasticity (log-log) term that can't blow up. | Tested it: RMSE ₹406k → ₹56k, OOF R² 0.775 → 0.812, worst miss ₹11.9M → ₹0.4M — same one model. Kept. |
| Missingness | "The `floor_missing` flag is computed in cleaning but the model ignores it — bug?" | Wire the imputed-floor indicator in: it's a data-quality flag (no leak) and lets the model learn that listings hiding their floor differ. | Added: OOF R² 0.812 → 0.818, CV spread 0.042 → 0.033 (steadier). Kept. |
| Missing BHK | "12% of rows have no BHK — drop or impute?" | Suggested inferring from area (~450 sqft/BHK) rather than dropping, and **flagging** the imputation. | Kept the infer-and-flag approach; documented it as an assumption. |
| SQL | Draft of the window-function and CTE queries | Gave a working `RANK() OVER` + `AVG() OVER ()` skeleton and a metro-band CTE. | Kept structure; verified every number against the actual DB output before trusting it. |
| Prose | Draft README/memo structure | Organised "business impact first, code second". | Rewrote in my own voice; the walkthrough video is fully mine. |

## The moment it was confidently wrong

**Claim:** Early on, the LLM confidently recommended I engineer `rent_per_sqft` as a **model feature** to "boost accuracy," presenting it as an obvious win.

**Why it's wrong:** `rent_per_sqft = price / area_sqft`. The target *is* `price`. Feeding rent-per-sqft into a model that predicts rent leaks the answer — the model would post a near-perfect R² that means nothing, because at prediction time for a new flat you don't yet know its rent, so you can't compute its rent-per-sqft. It's textbook **target leakage**, and the LLM stated it with no hesitation.

**How I caught it:** The accuracy looked *too good* in a quick test (R² near 0.99). Results that look too perfect are a red flag, not a victory — so I traced the feature back to its formula and saw `price` on both sides. I removed per-listing `rent_per_sqft` from the feature set.

**The nuance I kept — then hardened:** I kept the *locality-level* rent/sqft signal (the per-listing version leaks the exact answer for that row; the neighbourhood level encodes "how expensive is this area," which is knowable before pricing a new flat and mirrors how a human prices one). But a leave-one-out check showed the plain locality median *still* leaked for single-listing localities — there the "neighbourhood median" simply is that one flat. So I switched the model to a **leave-one-out** median (`median_rps_loo`): each flat sees only the *other* flats in its locality. Reject the leaky feature, keep the defensible proxy, then close the residual leak — that sequence is the judgment on display, mine not the model's. Closing the leak lowered the score by design; I kept the honest, lower number rather than the inflated one. (The final model, after also fixing the area specification and wiring in the `floor_missing` flag noted in the table above, reports OOF R² **0.818**.)

## Where I trusted AI and where I did not

- **Trusted:** boilerplate, SQL skeletons, the log-target argument, prose structure — all cheap to verify and I verified them.
- **Did not trust:** anything touching correctness of numbers or the honesty of the model. Every metric in this repo was regenerated by running the code, not copied from an LLM's claim. The confidently-wrong leakage suggestion is exactly why: an LLM will assert a plausible, wrong thing in the same confident tone it uses for correct ones, so the check has to be *mine*.
